# Пулы аккаунтов и паузы парсера

Production-парсер рекомендаций запускается командой `npm run parse:sources`. Аккаунты берутся из общей таблицы `accounts` с `pool='parser'` и `status='active'`; дополнительно учитываются `SESSION_STRING_PARSER_*` из ENV.

Изменение пула в БД подхватывается при запуске процесса. При переводе аккаунтов из комментатора спам-метки в `account_bans`, сессии и остальные данные не удаляются. Перевод не снимает ограничения Telegram и не гарантирует доступность рекомендаций.

## FLOOD_WAIT

- При старте парсер читает активные паузы из существующей `account_flood_wait`, только для имён своего пула.
- Аккаунты с будущим `unlock_at` пропускаются. Новые доступные аккаунты могут работать сразу, не ожидая весь старый пул.
- Новый FLOOD_WAIT сохраняется в БД перед переключением на следующий аккаунт.
- Если доступных аккаунтов нет, парсер ждёт ближайшего допустимого кандидата, добавляя минутный буфер.
- Исключённые в текущем процессе аккаунты без Premium и с отозванной сессией не выбираются из очереди ожидания.
- При недоступной БД загрузка/сохранение пауз завершается ошибкой, а не продолжает запросы без учёта ограничений.

Схема БД не меняется. Перезапуск не обнуляет сохранённые сроки. Сам парсер всё ещё может вводить отдельную 24-часовую паузу после своей проверки спама: она записывается с причиной `SourcesParser spam-check cooldown`, а не выдаётся за ответ Telegram FLOOD_WAIT. Проверка Premium по количеству рекомендаций этим изменением не переработана.

Паузы старой версии, хранившиеся только в памяти, перед первым обновлением нужно перенести из актуальных логов в БД. Если есть отложенный таймер перезапуска для смены пула, после успешного ручного обновления его нужно отменить, чтобы не перезапустить рабочий парсер повторно.

Проверка без обращения к Telegram:

```sh
npx tsc --noEmit --pretty false
NODE_ENV=production npx ts-node src/scripts/utils/testParserFloodPersistence.ts
```
