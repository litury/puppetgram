# Диагностика API комментатора

Диагностика включена только для клиентов `autoCommentSimple`, которым передано имя аккаунта. Она не меняет пул каналов, паузы, число повторов GramJS или обработку FLOOD_WAIT. Миграций БД нет.

## События

- `rpc_diagnostics_started`: версия GramJS и идентификатор экземпляра клиента.
- `rpc_attempt`: аккаунт, API-метод, `clientId`, `requestId`, номер `attempt`.
- `rpc_result`: те же идентификаторы, успех, длительность, категория ошибки, числовой RPC-код и `waitSeconds`, если есть.
- `rpc_diagnostics_unavailable`: внутренний интерфейс SDK несовместим с адаптером; статистику нельзя считать полной.

Попытки учитываются на `MTProtoSender.addStateToQueue`, ниже `client.invoke`. Поэтому короткий FLOOD, автоматически обработанный GramJS, и следующая попытка видны отдельно. Адаптер проверяется тестом с настоящим циклом `invoke` установленной библиотеки; после обновления GramJS тест обязателен.

Это количество постановок RPC в очередь SDK, **не число пакетов на проводе и не скрытый счётчик Telegram**. Транспортные перепосылки после обрыва, прямой `sender.send`, авторизационный handshake и обращения из других приложений аккаунта не учитываются. Ошибки до постановки RPC в очередь не считаются попытками. При аварийном завершении `rpc_attempt` может остаться без `rpc_result`; такую попытку нельзя считать успешной.

Полные запросы, ответы, тексты комментариев, адресаты, `access_hash`, сессии, пароли и тексты исключений не записываются. `slowmode_wait` отделён от `flood_wait`. `clientId` меняется при создании клиента, поэтому аналитику аккаунта нужно объединять между клиентами и перезапусками.

## Хранение

`TELEGRAM_API_DIAGNOSTICS=0` отключает диагностику. По умолчанию она включена.

События поступают в существующий JSON-логгер на уровне `info`. Для файлового архива задайте:

```env
TELEGRAM_API_DIAGNOSTICS=1
TELEGRAM_API_DIAGNOSTICS_DIR=/var/log/puppetgram/telegram-api
```

Архив: `telegram-api.jsonl` плюс девять ротаций `.1`–`.9` по 10 MiB (около 100 MiB суммарно). `.1` — самая свежая ротация. Хранение ограничено объёмом, а не гарантированным числом дней. Файлы создаются с правами `0600`, каталог — `0700`. Запись выполняется сразу, без буфера приложения; это не гарантия от потери данных при аварии диска/хоста.

Один каталог рассчитан на **один процесс-писатель**. При нескольких репликах или перекрывающемся start-first редеплое нужны разные каталоги либо внешний сборщик. Для текущей одиночной реплики используйте stop-first обновление. Ошибки диска не прерывают комментирование: появляется предупреждение `archive_write_failed`, повторная попытка записи через минуту, события продолжают поступать в stdout. Пропущенные файловые события автоматически не восстанавливаются.

### Docker Compose

`docker-compose.production.yml` подключает именованный volume `puppetgram-commenter-api-diagnostics`. Он сохраняет архив при пересоздании контейнера. Не удаляйте volume командой `down -v`. Локальный volume не защищает от потери сервера и не переносится автоматически на другой узел Swarm.

### Dokploy Application

Production-комментатор развёрнут как отдельное приложение Dokploy; изменение Compose-файла **не меняет его настройки**. До следующего редеплоя в настройках этого приложения необходимо:

1. Добавить Volume Mount: имя `puppetgram-commenter-api-diagnostics`, путь `/var/log/puppetgram/telegram-api`.
2. Добавить две переменные из примера выше, не заменяя остальные ENV.
3. Проверить одну реплику и stop-first порядок обновления.
4. После редеплоя проверить mount, событие `rpc_diagnostics_started`, записи в файле и отсутствие предупреждений архива.
5. При следующем пересоздании контейнера убедиться, что записи с предыдущим `clientId` сохранились.

Без mounted volume путь внутри контейнера не обеспечивает сохранность после редеплоя. Без `TELEGRAM_API_DIAGNOSTICS_DIR` выводится `archive_not_configured`, работают только консольные логи. Внедрение кода само по себе не означает, что production-архив уже подключён.

## Как анализировать

За 2–3 рабочих цикла сгруппировать `rpc_attempt` по аккаунту и методу; отдельно посчитать результаты и повторы (`attempt > 1`). Сопоставить `rpc_result` с `errorType=flood_wait` и `waitSeconds` с успешными публикациями из существующей таблицы `comments` за тот же период. Не считать все RPC успешными комментариями и не выводить точный лимит Telegram из одного наблюдения.

Ключ пары попытка/результат — `(clientId, requestId, attempt)`. Если анализируются и stdout, и файловый архив, одинаковые события нужно дедуплицировать ещё и по `event`. Для коротких FLOOD `waitSeconds` берётся из исходной ошибки до внутреннего повтора; таймер ожидания SDK не изменён.

Проверка без подключения к Telegram:

```sh
npx tsc --noEmit --pretty false
npx ts-node src/scripts/utils/testRpcDiagnostics.ts
```
